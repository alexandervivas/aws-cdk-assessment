# 0007. One CDK Stage per environment, configuration in code

Status: Accepted, 2026-10-21.

## Context

The service must deploy at least as `dev` and `prod` from the same code, and the stages must not collide or drift.

## Decision

`PersonServiceApp` creates a `Dev` and a `Prod` `PersonServiceStage`, each holding one `PersonServiceStack`. Every difference between them is a field of the `EnvironmentConfig` record (`infra/.../EnvironmentConfig.java`): log level and retention, removal policy, deletion and termination protection, point-in-time recovery, API rate and burst, reserved concurrency, alarm thresholds and event archive retention. The record rejects inconsistent values, for example a burst above reserved concurrency.

- Accounts come from `-c devAccount` and `-c prodAccount` (both or neither, and different) or from `CDK_DEFAULT_ACCOUNT`. The region defaults to `eu-west-1`. No account ID is committed.
- Resource names are generated by CloudFormation. The bus is the exception: `person-events-{stage}`. The API is named `person-service-{stage}`.
- Snapshot tests of both templates catch unintended drift.

## Consequences

- Adding a stage means one more config factory and one more stage in the app.
- Without account context both stages deploy to one account. That works, but see [0014](0014-account-level-apigateway-logging-role.md) for the shared API Gateway setting.
- The alarm thresholds exist in the config, and the alarms themselves are planned ([status](../roadmap.md)).

## Rejected alternatives

- Copy-pasted stacks per environment: they drift.
- CDK context or environment variables for every setting: values scatter and are not type-checked or tested.
